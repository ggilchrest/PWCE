# Trusted Gateway admission and invocation

`GatewayService.requestTrustedDispatch` is an internal host API for the trusted dispatcher. The ordinary Agent request route does not expose this method. The separately authenticated dispatch transport below invokes it. The ordinary `/gateway/v1/request` route continues to reject `authority.authorizeDispatch`, including requests containing `trusted`, `trustedDispatch` or `phase` fields. Do not select this host API using a field in an Agent request. The dedicated transport separately authenticates the dispatcher and requires its published contract digest.

The host calls the two phases with the original Agent token, current authority context, identity, world, execution mode, explicit retained snapshot, exact action parameters and idempotency key:

1. `authority.authorizeDispatch` checks the producer's policy, grant, approval, snapshot and target preconditions and commits the admission. The response contains the producer's stored `admission`, its `actionRef`, original `decision`, current action status and duplicate flag. It does not call the target. Approval-required responses retain the existing pending Human review workflow; approval alone does not admit or dispatch.
2. `capabilities.invoke` additionally requires that original `actionRef`. It resolves the existing action and verifies the same normalized request, idempotency key, approval requirements/reference and exact retained snapshot before calling the producer's single-claim dispatcher. It never calls admission or creates a replacement action.

Both phases authenticate and recheck current context, identity, grant revision, snapshot and deadline after asynchronous work. Invocation cannot extend the original action deadline. The dispatcher retains its existing approval recheck, fresh target check, durable started marker and uncertain-outcome behavior.

Repeated admission returns the original record. The ordinary combined Gateway invocation cannot start an action already admitted through the split path: its duplicate handling remains a read. Repeated trusted invocation uses the original durable attempt; concurrent calls share one dispatch and unknown results remain unknown. Status reconciliation remains the existing read operation and cannot authorize a new effect.

The stored record is producer admission evidence, not a Lifestream `AuthorityDispatchResult`, a remote credential, or confirmation of an effect. No Lifestream receipt is manufactured here. The core Gateway bundle bytes and existing 1.0.0 request route are unchanged. The separate dispatch transport has its own versioned bundle and exact core dependency.

## Remaining integration

The configured Lifestream path still needs the consumer digest lock, canonical authority/capability mapping, admission evidence mapping, and joined action verification. This internal prerequisite does not make that path usable or verified. Contexts and snapshot custody remain process-local: a fresh Gateway process cannot dispatch an old admission using reconstructed context or a replacement snapshot. Read-only outcome recovery must remain distinct from permission to send a command.

Tests in `test/gateway-trusted-dispatch.test.js` use synthetic targets and synthetic host approval proof. They do not establish physical effects, selected-provider behavior, or Human acceptance.

## Authenticated transport

The public extension is `pwce-trusted-dispatch.v1@1.0.0`, in `contracts/gateway-dispatch`. Its bundle pins the transport description and request/response schemas, and requires the existing exact core Gateway bundle. Regenerate it with `node scripts/generate-dispatch-bundle.mjs --write`; omission of `--write` checks byte identity.

Startup may configure `PWCE_GATEWAY_DISPATCHER_TOKEN`: a 32–512 character printable ASCII secret, distinct from the Agent and Studio credentials. Absence disables the dispatch routes; this is never inferred from the ordinary token. Keep this secret in the trusted host configuration, outside model context, requests, browsers and source control. Adding the code does not configure or restart a saved deployment.

- `GET /gateway/v1/dispatch/bundle` requires `Authorization: Bearer <Agent token>` and `X-PWCE-Dispatcher-Token: <dispatcher secret>`.
- `POST /gateway/v1/dispatch` requires both credentials, JSON content type, and `X-PWCE-Dispatch-Contract` equal to the negotiated bundle digest. Wrong digest returns 409 before admission.
- A request with an `Origin` header is rejected. Only the separately configured host transport should hold the dispatcher secret.
- The request must supply both dispatch profile fields, the full core profile/identity/request/correlation/world/environment/deadline envelope, original retained snapshot, capability/version/operation, target/site/parameters, key and approval fields. Nullable identity and approval references must be explicit. Only invocation supplies `actionRef`.
- Unknown fields, body credentials, unsupported operations, duplicate participants, missing values and published bound violations are rejected before admission. The same 1 MiB transport cap applies. The response adds the dispatch profile identity to the original producer result. No automatic retry occurs in the producer.

The standalone `scripts/gateway-dispatch-fixture.mjs` process is a synthetic transport fixture for cross-repository conformance. It requires fresh `PWCE_FIXTURE_TOKEN` and `PWCE_FIXTURE_DISPATCHER_TOKEN` values supplied by the test runner, listens only on loopback, and never configures a physical target. Readiness output contains only its URL and fixture markers. Bounded stdin commands read the target-call count, revoke the synthetic grant, or stop the process. The Lifestream runner uses this fixture through public HTTP, including an intentionally discarded completed reply; it does not import PWCE implementation code.

## Producer-owned admission proof

The trusted admission response now also contains `admissionEvidence`, a bounded projection of the original durable action. `pwce-action-admission.v1@1.0.0` publishes its complete schema and binding rules under `contracts/action-admission/`. Its independent bundle pins the existing trusted-dispatch and capability bundles; it does not rewrite either published bundle. Consumers must explicitly negotiate and pin this proof profile before interpreting it.

The proof carries the original action/key, normalized action fingerprint, principal, capability/version/operation, site/target/parameters, World and explicit identity scope, execution environment, grant revision, target identity, dispatch deadline, approval terms, retained snapshot bytes, admission precondition and admission time/decision. The fingerprint is canonical JSON text, not a hash. The published profile defines the canonicalization and snapshot-scope positions. Snapshot and precondition custody retain original JSON strings with SHA-256, so consumer object-key reordering cannot change their meaning or break their integrity check. The schema also defines the decoded snapshot and precondition documents.

The producer builds this proof only from a stored action returned by final admission. It checks the actual fingerprint, known capability, snapshot bytes and scope, original timestamps and precondition evidence before returning it. Mutable action status, attempt and result fields are excluded. Repeating admission after dispatch therefore returns identical proof and separate current action state. A corrupt record fails proof generation; it is never repaired into a new admission. A response failure after admission may leave the producer admission stored and does not imply rollback or permission to invoke.

`GET /gateway/v1/admission-contracts` returns the static public proof bundle. `GET /gateway/v1/admission-contracts/<schema-sha256>` returns exact schema text and artifact metadata. These definition reads require the Agent bearer token, never the dispatcher credential, and create no grant, approval, action or authority context. The actual admission response still requires the separate trusted dispatcher credential and all existing authority checks.

A proof is not a signature, a bearer credential, a target-call claim or effect confirmation. Original snapshot custody, current authority, target preconditions and approval still fence actual invocation. Lifestream must map the proof to its original invocation/input and retain the real evidence before final dispatch; complete canonical admission/invocation mapping remains outstanding. Verify publication with `node scripts/generate-admission-contracts.mjs` and run `node --test test/admission-evidence.test.js` for synthetic HTTP, immutable-proof and corruption coverage.
# Invocation and result evidence

The separately versioned public `pwce-action-invocation.v1@1.0.1` profile adds `invocationEvidence` to trusted invocation and qualified `capabilities.getInvocation` replies. Static Agent-authenticated GETs at `/gateway/v1/invocation-contracts` and `/gateway/v1/invocation-contracts/:sha256` expose the exact manifest and schema bytes. They create no context, action or approval and use no dispatcher credential. Regenerate/check the public bundle with `node scripts/generate-invocation-contracts.mjs [--write]`.

The proof binds current status to the unchanged original admission and the sole recorded dispatch attempt. It preserves the first `dispatchResult` separately from the current `result`, original producer timestamps and the latest reconciliation reference. Both result objects follow the already published light-result schema; the generated schema embeds exact copies of that schema and the admission schema, checked against their dependency pins. No Lifestream record or private schema is introduced. Existing core, dispatch, admission and capability bundles are unchanged.

Only full producer `succeeded` confirms success. Partial, failed, denied, rejected, cancelled, timed-out and unknown outcomes remain distinct. A failed reply with unknown physical effect now remains eligible for read-only reconciliation. A status query can preserve later confirmation but never admits, invokes or refreshes the original action deadline. A durable attempt identifies a dispatch claim, which may still be refused before reaching the target.

Evidence projection rejects inconsistent status/result, attempt identity, original admission, producer timestamps and reconciliation custody. Complete evidence is bounded to 131072 UTF-8 bytes; each result including host timestamps is bounded to 17000 bytes. Proof-generation failure after dispatch or reconciliation does not imply rollback or justify a replacement effect. Original legacy targets without a declared stable identity retain their scoped status view but omit proof with `invocationEvidenceUnavailable: original_target_identity_missing`; no qualified identity is invented. Missing or foreign actions disclose no proof. Lifestream must explicitly consume and verify this published profile before claiming canonical invocation/status coverage.

## Read-only recovery of a missing admission reply

The separately pinned `pwce-admission-recovery.v1@1.0.0` profile adds authenticated `GET /gateway/v1/admission-recovery/bundle` and `POST /gateway/v1/admission-recovery`. The POST requires `X-PWCE-Admission-Recovery-Contract` with the exact bundle digest. It uses the Agent bearer header and current original authority context; no dispatcher secret is needed because this operation cannot admit or dispatch. The existing core Gateway operation catalog and bundle remain unchanged. The ordinary `/request` route rejects `authority.recoverAdmission`.

The caller retains the original producer idempotency key, exact canonical fingerprint text, snapshot reference and approval terms before admission I/O. Lookup finds the single existing producer record, checks its principal, site, World, environment and complete Assistant/endpoint/participant/audience scope, verifies the original admission proof and binds it to the same authority context. A changed or absent tuple returns `unknown` with no action identifier. A known response contains only the original admission evidence and action reference; it does not report a current effect result.

The new read deadline is at most 30 seconds away. It never replaces the original producer deadline or admitted time, which are recovered only from the stored proof. Expired original admission and discovery lifetimes do not prevent an authorized historical read. Current context expiry, revocation and changes during the read still withhold evidence. Snapshot renewal, authority-context rotation or restoration, and new dispatch permission are not provided by this profile.

Lookup makes no authorization, precondition, invocation or reconciliation call. Actions and approvals are unchanged; the Gateway may append its normal request audit. An audit write failure withholds the response. Unknown is not evidence of absence and must not authorize replacement admission. Legacy records lacking a qualified target identity explicitly remain unavailable. Corrupt proof or duplicate original keys fail closed.

The public profile includes complete request/response schemas with the unchanged admission schema embedded by exact dependency identity. `node scripts/generate-admission-recovery-contracts.mjs` verifies ordered artifact bytes and generates the bundle without private imports. The raw request ceiling is 65,536 bytes and response ceiling is 131,072 bytes; default transport limits for other routes remain unchanged. Synthetic HTTP tests cover the discarded reply, current access, changed bindings, expiry during reads, write failure and unchanged target-call counts. Reopening the action store demonstrates persistence of original admission; restoration of a stopped Gateway's authority contexts remains outside this component's claim.
