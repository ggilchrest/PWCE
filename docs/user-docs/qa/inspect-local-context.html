QA: Inspect local context and request a safe action

Part of: Inspect local context and request a safe action

Purpose

Verify that a developer can authenticate to Studio, inspect authorized Home Assistant evidence, preview a reversible action, complete local approval, read its approval status, and dispatch it while seeing an honest persisted outcome. Also verify that an external Assistant cannot replace connection authentication through request data, and that uncertain or historical results keep their supporting evidence and time boundaries. Event connections must stop when their authority expires or changes. Interrupted actions must keep an honest outcome and must not repeat automatically. An external request must reach a separately authenticated Human review before its original scope can resume. Capability lists must remain tied to the reviewed scope and be checked before an action starts. Fresh target reads must prevent a command when the selected light is unavailable.

Preconditions

  • Configure the local Studio username, password, and comma-separated recovery codes when Human access is enabled.
  • Run the local Home Assistant development container or seed the PWCE development state.
  • Start PWCE Studio with npm run dev and open http://127.0.0.1:4173/.

Acceptance Criteria

Context qualification criteria

Testing Instructions

  1. Open Studio and sign in.

    Invalid credentials fail; valid credentials open the authorized site view.

  2. Review runtime, current state, evidence, and explanation.

    Health, knowledge, source, time, and limitations are visible.

  3. Choose a brightness and select Preview request, then Request approval.

    The request has an approval reference and no external effect occurs.

  4. Read GET /api/approvals/<approvalRef> with the authenticated session.

    The response exposes the site-qualified approval status, expiry, and approval metadata without exposing secrets.

  5. Select Approve locally, then read the same approval reference again.

    The status is approved; dispatch remains a separate step.

  6. Select Dispatch approved action.

    The persisted Action status is shown. An unverified service acknowledgement remains outcome_unknown.

  7. Sign out, then sign in with one recovery code and try that code again.

    The first recovery sign-in succeeds and reuse fails.

External Assistant authentication check

Use a disposable fixture environment for this check; do not change your live Home Assistant configuration or copy a real token into a test.

  1. From the PWCE checkout, run node --test test/gateway-http.test.js.

    The fixture checks valid header authentication, rejects a token supplied in the body, rejects non-object bodies, and denies a wrong header even with a known authority reference. It uses synthetic credentials and makes no Home Assistant call.

Assistant approval criteria

Assistant approval: testing instructions

  1. In a disposable synthetic environment, submit a Gateway light request that requires approval, then sign in to Studio with the local password.

    The request appears under Assistant action requests. The target has not been called.

  2. Follow Review an Assistant action request, including its desktop, phone and approved-state screenshots.

    The displayed fields match the original request. The approval button remains disabled until you confirm review. Approval leaves the target untouched.

  3. Explicitly resume that same Gateway request with its approval reference, then repeat it.

    The first request completes against the synthetic target; the duplicate returns the same action and does not call it again.

  4. From PWCE, run node --test test/gateway-approvals.test.js.

    The HTTP tests cover separate Human authentication, unchanged scope, expiry, concurrent review, foreign sites, logout during approval and corrupt evidence. No real device is used.

  5. With Playwright installed, run node scripts/check-gateway-review-browser.mjs. If needed, set PLAYWRIGHT_MODULE to its module path and BROWSER_EXECUTABLE_PATH to a disposable Chromium-compatible browser executable.

    The check starts and stops its own synthetic service and browser. It checks password sign-in, complete fields, keyboard use, 390px and 320px layouts, approval without dispatch, one explicit target call, reload, text safety, pagination and sign-out.

Edge cases

  • Missing or partial auth configuration → startup fails closed.
  • Unknown or out-of-scope approval reference → not found or scope denied.
  • Expired approval → expired and dispatch denied.
  • Live effects disabled → the live route is denied.
  • Service acknowledgement without matching state → result stays outcome_unknown.

Original admission proof checks

  1. From PWCE, run node scripts/generate-admission-contracts.mjs and node --test test/admission-evidence.test.js.

    The generated definition matches its published bytes, and all six synthetic checks pass. They use temporary local HTTP listeners and synthetic targets. A successful admission has zero target calls. Reading its original proof after one explicit synthetic dispatch does not send another command. These checks do not exercise a real device or complete the Lifestream workflow.

Original result proof checks

  1. From PWCE, run node scripts/generate-invocation-contracts.mjs and node --test test/invocation-evidence.test.js test/action-gateway-http.test.js.

    The generated public definitions match their pinned bytes. The synthetic checks pass for all eight terminal result types, in-flight status, original replies, later confirmation, legacy target identities and rejected corrupt records. Status checks never add a target invocation. The tests use temporary local HTTP listeners; they do not contact a real device or enable the Lifestream control plane.
